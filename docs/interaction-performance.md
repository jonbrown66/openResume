# 组件打开延迟：测量与修复

用户反馈打开、显示变慢后，本轮对点击至组件内容显示进行单独测量，没有将功能 E2E 通过当作性能证据。

## 测量方法

`e2e/open-performance.spec.ts` 使用 Chromium、隔离的浏览器上下文和本地生产服务，串行运行桌面与移动视口。每类组件首次打开一次、再打开两次。从真实 pointerdown 开始，以 requestAnimationFrame 观察目标内容的布局与祖先透明度：

- 首帧：内容有尺寸，累计透明度超过 0.05。
- 显示完成：累计透明度达到 0.99。

测量不是 INP、FPS、物理手机性能，也没有模拟慢网或 CPU 限速。首开指浏览器上下文内首次打开组件；服务端已经构建，不是开发服务冷编译。小样本仅用于定位和本机前后比较，不能视作 p95 或对所有设备的保证。计时文件作为 Playwright 附件保留。

## 发现

设置、样式面板和助手原先在点击后才通过 React.lazy/Suspense 加载。生产版本首次打开也出现约 300ms 的 fallback 等待；开发模式不是唯一原因。重复打开没有代码加载等待，但 180ms 入场让显示完成仍需约 120–140ms。部分入口的 fallback 为 null，等待期间缺少反馈。

直接将所有次级界面加入首屏能消除等待，但实测 First Load JS 从 296kB 增至 366kB，因此未保留该方案。

## 最终修改

- 设置、样式和助手使用模块缓存与 useSyncExternalStore 加载包装，不经过交互路径上的 Suspense fallback 延迟。
- 首屏绘制后的浏览器空闲阶段预加载这些模块；没有 requestIdleCallback 时延后 100ms 启动。早于预加载的点击也会立即启动加载，并显示面板加载提示或助手忙碌状态。
- 只提前加载代码，尚未打开的表单和聊天组件不提前挂载，避免读写用户配置或执行聊天逻辑。
- 区块编辑和 CSS 编辑器直接可用；PDF、DOCX、文件提取等大型依赖仍按原业务路径加载。
- 高频浮层改用 120ms 入场；助手减少移动距离；CSS 编辑器移除父子叠加的入场淡入。
- 加载失败交给现有 ErrorBoundary，未吞掉错误。模块只请求一次，预加载与打开共享同一份结果。

最终 First Load JS 为 **301kB**，比修复前增加约 5kB。构建指标不等于实际网络下载或首屏时间；没有把它表述为加载时间改善。

## 生产测量结果

单位 ms，均为“首次打开的内容首帧 / 显示完成”。

| 组件 | 桌面修复前 | 桌面修复后 | 移动视口修复前 | 移动视口修复后 |
| --- | ---: | ---: | ---: | ---: |
| 设置 | 320 / 320 | 39 / 110 | 317 / 317 | 33 / 106 |
| 样式 | 315 / 430 | 16 / 94 | 321 / 435 | 16 / 91 |
| AI 助手 | 310 / 310 | 5 / 5 | 312 / 312 | 8 / 8 |
| 导出菜单 | 6 / 121 | 10 / 82 | 13 / 120 | 10 / 83 |

助手首次挂载保留原有 `AnimatePresence initial={false}` 行为，因此首次显示没有入场等待；重复打开仍执行短入场。首帧几毫秒差异受采样与调度影响，不据此声称导出首帧变快。

修复后两次重复打开的显示完成范围：设置 84–91ms，样式 85–90ms，助手 82–85ms，导出 83–86ms。额外检查 CSS 首开为桌面 24/83ms、移动视口 22/88ms；区块首开为桌面 17/17ms、移动视口 15/15ms。额外两类没有有效修复前计时，不作数值对比。

开发模式在模块尚未编译时仍可能等待首次编译；本轮有一次设置内容首开约 509ms，加载反馈会立即出现。空闲预加载可以提前触发编译，无法消除开发服务器本身的编译成本，不能承诺 localhost 开发环境所有首开都在 100ms 内。

## 验证

lint、类型检查、生产构建通过；Vitest 139/139 通过，包含加载反馈及时替换、预加载复用和当前 props 正确性。生产性能采样用例 2/2 通过。

完整功能回归首次运行 71/72 通过；唯一失败是菜单行高的动画坐标返回 35.999992px，而实际布局高度为 36px。断言改用 clientHeight 读取布局尺寸，保留至少 36px 的要求；相关桌面、移动用例随后 2/2 通过，72 个功能场景均已覆盖。没有删除用例或降低行高标准，未发现加载方式变更引入的业务回归。
